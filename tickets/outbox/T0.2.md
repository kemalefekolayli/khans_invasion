## Summary
Created the autoplay smoke-test harness. `SimulationController` is a MonoBehaviour that waits for `GameEvents.OnPlayerNationReady`, then advances turns via `TurnManager.Instance.EndPlayerTurn()` on a serialized cadence, asserting invariants per turn (no negative gold, no negative pop, `TurnManager` not stuck in a phase, no exceptions/null refs) and writing a PASS/FAIL report to `Logs/simulation_report.txt` (project root, gitignored). It supports AI-only and scripted-player modes; scripted mode also drives player armies (`Army.MoveToProvince`) and raids (`RaidManager.ExecuteRaid`) through public APIs. It is inert unless `autoStart` is set or a headless run is requested, so it is safe to leave in a scene. `SimulationRunner` is the headless driver (`#if UNITY_EDITOR`): loads `GameScene`, enters Play Mode, lets the harness finish and write its report, exits Play Mode, and in batchmode exits the editor with a 0/1 exit code. Invokable via `-executeMethod Khans.Invasion.Testing.SimulationRunner.Run` and `[MenuItem("Tools/Simulation/Run Headless")]`.

No game systems were modified. No scene changes were needed — the harness spawns itself at runtime via a `[RuntimeInitializeOnLoadMethod]` boot flag (same pattern as `ArmyBattleManager.EnsureRuntimeInstance`), so GameScene is untouched.

## Notes / Issues
- **Namespace:** the codebase uses the global namespace everywhere, but the ticket mandates the exact `-executeMethod` target `Khans.Invasion.Testing.SimulationRunner.Run`, so the new classes live in `namespace Khans.Invasion.Testing`. This is the only namespaced code in the project — flagged deliberately.
- **Boot-flag design:** `SimulationRunner.Run()` sets `SimulationController.RequestRun(...)` then enters Play Mode; a `[RuntimeInitializeOnLoadMethod(AfterSceneLoad)]` spawns the controller. No GameScene YAML edit needed (avoids a risky manual scene edit). Manual scene placement is still supported via `autoStart=true`.
- **Safety guard:** a controller left in a scene with `autoStart=false` is fully inert (`armed` flag prevents the watchdog from firing), so normal play is unaffected.
- **Batchmode behavior:** on returning to Edit Mode, if `Application.isBatchMode`, the editor exits with code 0 (PASS) / 1 (FAIL). The controller force-fails and exits play mode on a 120s timeout if the game never becomes ready.
- **How to run (for tester):** `Unity.exe -batchmode -nographics -projectPath <root> -executeMethod Khans.Invasion.Testing.SimulationRunner.Run -quit` — note `-quit` must NOT be combined with play-mode entry; the runner exits the editor itself via `EditorApplication.Exit(0|1)`. Read `<root>/Logs/simulation_report.txt`.

### Game bugs / observations noted while building (do NOT fix here — future tickets)
1. **Confirmed StartMenu bug:** `StartMenu.gameSceneName` defaults to `"SampleScene"` and `Assets/Scenes/SampleScene.unity` does not exist (only `StartScene.unity` and `GameScene.unity`). Start→GameScene is broken as the planner stated. The harness does not depend on the StartMenu path (it loads GameScene directly).
2. **TurnManager AI-turns not exception-guarded:** `ProcessAITurns()` (TurnManager.cs:106) invokes `OnAITurnsStart`/`OnAITurnsComplete` without a try/catch, unlike the end-turn processors which are wrapped. An exception inside an AI nation's `ProcessTurn` would abort the whole `EndPlayerTurn()` chain and leave `CurrentPhase` stuck in `AIProcessing`. Worth a robustness ticket (e.g. wrap AI processing per-nation).
3. **No negative-gold guard in gameplay:** nothing in game systems clamps or checks `NationModel.treasury` below zero; the harness is currently the only invariant enforcement. Fine for now, but future economy tickets should consider the invariant.
