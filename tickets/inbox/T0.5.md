# TICKET: T0.5 — ArmyBattleManager: stop O(n²) scan + per-frame list allocations

## Context
`ArmyBattleManager.Update()` (Assets\code\Chars\WarMechanics\ArmyLogic\ArmyBattleManager.cs:56-102) runs EVERY frame:
- `ArmyManager.GetAllArmies()` (ArmyManager.cs:77) allocates `new List<Army>(allArmies)` per call → heap alloc every frame
- a nested double-for O(n²) pair loop over all live armies, computing `sqrMagnitude` distances
- `UpdateBattles()` (line 214) also allocates `new List<int>(activeBattles.Keys)` per frame

Fine at ~5 armies, painful at scale. This is the primary combat-per-frame cost.

## Must Have
- [ ] No per-frame list allocation from `GetAllArmies()`: either expose a cached read-only view or a dirty-flagged cached copy in `ArmyManager` (invalidated on register/unregister), or iterate the internal list directly without copying.
- [ ] The pair scan is throttled (e.g. only every `scanInterval` ~0.3–0.5s) OR skipped when `ArmyManager` has no new/moved armies (dirty flag). Battle proximity radius is small (0.75); an interval scan is sufficient for a strategy game.
- [ ] `UpdateBattles()` reuses a buffer instead of allocating a key list per frame.
- [ ] Battle behavior unchanged: battles still trigger when hostile armies meet.

## Nice to Have
- [ ] A simple spatial grid (cell size ~ battle radius) so only nearby army pairs are compared, replacing O(n²) at scale.
